# Trend Leader GitHub Write Safety Policy

> 문서 버전: v1.0
> 작성 기준일: 2026-09-11
> 적용 대상: GitHub 연결을 통한 파일 생성 및 기존 파일 수정·삭제, 관련 문서 작업
> 문서 역할: GitHub 쓰기 작업의 변경 안전성 기준

---

## 0. 문서 목적

이 문서는 Trend Leader에서 GitHub 연결을 통해 파일을 수정할 때 다음 위험을 줄이기 위한 안전 정책이다.

- 오래된 파일 내용을 기준으로 최신 변경을 덮어쓰는 문제
- 필요한 부분만 수정하면 되는 작업에서 전체 파일을 불필요하게 재작성하는 문제
- 같은 파일에 대한 동시 변경을 감지하지 못하는 문제
- AI가 의도한 수정 범위보다 넓은 변경을 함께 포함하는 문제
- GitHub Contents API의 전체 파일 교체 방식 때문에 부분 변경 의도가 사라지는 문제

이 정책은 기능별 설계 확정안의 도메인, API, 데이터 모델 또는 구현 결정을 변경하지 않는다.

---

## 1. 핵심 원칙

GitHub의 기존 파일 수정은 기본적으로 **Patch-first** 방식으로 수행한다.

GitHub Connector의 최종 파일 업데이트가 전체 파일 내용을 교체하는 방식이더라도, 변경을 설계하는 과정에서는 파일 전체를 처음부터 다시 작성하지 않는다.

기본 흐름은 다음과 같다.

```text
최신본 조회
→ planning SHA 확보
→ 최소 변경 범위 식별
→ 최소 patch/diff 생성
→ 쓰기 직전 최신본 재조회
→ SHA 및 context 충돌 검사
→ 최신본에 patch 적용
→ 최종 diff 검증
→ 최신 SHA로 GitHub 쓰기
```

---

## 2. Planning SHA와 Write SHA

파일 수정 계획을 세울 때 처음 읽은 파일의 blob SHA를 `planning SHA`로 취급한다.

실제 쓰기 직전에는 대상 브랜치에서 같은 파일을 다시 읽고 최신 blob SHA를 확인한다.

```text
planning_sha == latest_sha
→ 최초 계획 이후 파일 변경 없음
→ 기존 patch 적용 가능
```

```text
planning_sha != latest_sha
→ 최초 계획 이후 파일 변경 발생
→ 변경 범위 충돌 검사를 먼저 수행
```

최종 GitHub 쓰기에는 반드시 쓰기 직전에 확인한 최신 SHA를 사용한다.

오래된 planning SHA를 최종 쓰기 SHA로 재사용하지 않는다.

---

## 3. 최소 변경 원칙

기존 파일을 수정할 때는 다음 순서를 따른다.

1. 변경 목적을 먼저 정의한다.
2. 변경에 필요한 최소 구간을 식별한다.
3. 해당 구간의 앞뒤 context를 함께 확인한다.
4. 변경되지 않아야 할 부분은 그대로 보존한다.
5. 파일 전체 재구성보다 국소적인 수정이 가능한지 먼저 판단한다.

다음과 같은 이유만으로 전체 파일을 다시 작성하지 않는다.

- 파일이 짧다는 이유
- Markdown이나 JSON처럼 텍스트 기반이라는 이유
- 전체 내용을 한 번 읽었다는 이유
- 최종 API가 전체 파일 교체 방식이라는 이유

전체 재작성은 실제 작업 목적 자체가 문서 전면 개편, 전체 포맷 변환 또는 구조 전체 교체인 경우에만 허용한다.

---

## 4. SHA 변경 시 처리

쓰기 직전 최신 SHA가 planning SHA와 다르면 자동으로 오래된 결과를 덮어쓰지 않는다.

먼저 최초 planning 시점과 최신본 사이에서 변경된 영역이 현재 patch 대상과 겹치는지 판단한다.

### 4.1 비중첩 변경

최신 변경이 현재 patch 대상과 명확히 다른 영역에 있는 경우:

```text
최신본 기준으로 patch context 재검증
→ 최신본에 patch 재적용
→ 전체 diff 재검증
→ 최신 SHA로 쓰기
```

기존 전체 파일 사본을 사용하지 않는다.

### 4.2 중첩 또는 판단 불가

다음 중 하나라면 자동 쓰기를 중단한다.

- 다른 변경이 patch 대상 구간과 겹침
- 예상한 원문 context가 최신본에서 일치하지 않음
- 같은 문장이 여러 위치에 있어 적용 위치를 확정할 수 없음
- 최신 변경의 의미를 보존하면서 자동 병합할 수 있는지 불명확함
- 최신본이 설계 또는 계약 자체를 변경한 것으로 보임

이 경우 충돌 사실과 영향을 받는 구간을 사용자에게 먼저 보고한다.

### 4.3 실제 쓰기 시점의 충돌

쓰기 직전 재조회 이후 실제 GitHub write 사이에도 다른 변경이 들어올 수 있다.

최신 SHA로 write를 시도했는데 stale SHA 또는 동시 변경으로 충돌한 경우, 기존 완성본이나 기존 patch 결과를 새 SHA에 그대로 재전송하지 않는다.

다음 절차로 처음부터 다시 검증한다.

```text
write conflict
→ 최신 파일과 SHA 재조회
→ patch 대상 context 재검증
→ 중첩 여부 재판단
→ 최신본에 patch 재적용
→ 최종 diff 재검증
→ 새 latest SHA로 write 재시도
```

중첩 변경 또는 context 불일치가 발견되면 자동 재시도하지 않고 중단한다.

---

## 5. Context 검사

patch는 줄 번호만으로 적용하지 않는다.

다음 정보를 함께 사용한다.

- 대상 문장 또는 구조
- 앞뒤 문맥
- Markdown heading, 함수명, 타입명, JSON key 등 의미 있는 anchor

원래 기대한 context가 사라졌다면 임의로 가장 비슷한 위치에 적용하지 않는다.

---

## 6. 최종 쓰기 전 검증

최종 파일을 GitHub에 기록하기 전에 최소한 다음을 검증한다.

1. 요청한 변경이 모두 포함되었는가
2. 요청하지 않은 구간이 변경되지 않았는가
3. 최신본에서 새로 들어온 변경이 보존되었는가
4. Markdown/JSON/YAML/코드 문법이 깨지지 않았는가
5. 중복 heading, 중복 문단, 중복 import 또는 중복 key가 생기지 않았는가
6. 기능별 설계 확정안이나 API 계약을 의도치 않게 변경하지 않았는가

가능하면 전체 결과보다 **최종 diff**를 중심으로 검증한다.

---

## 7. 동일 파일 병렬 쓰기 금지

같은 파일에 대한 GitHub update/delete 작업을 병렬로 실행하지 않는다.

연속해서 같은 파일을 수정해야 한다면:

```text
첫 번째 쓰기 완료
→ 반환된 최신 content SHA 또는 파일 재조회
→ 두 번째 변경 계획 및 검증
→ 다음 쓰기
```

순서로 처리한다.

서로 다른 파일이라도 상호 의존적인 계약을 동시에 변경하는 경우 최종 정합성을 별도로 검증한다.

---

## 8. 여러 파일 변경

여러 파일을 수정할 때 각 파일의 SHA와 patch를 독립적으로 관리한다.

한 파일의 최신 여부를 확인했다는 이유로 다른 파일도 최신이라고 가정하지 않는다.

각 파일마다 최소한 다음 상태를 가진다.

```text
path
planning_sha
latest_sha
patch_target
conflict_status
write_status
```

하나의 변경이 다른 파일의 계약에 영향을 주는 경우 전체 변경 완료 전 교차 검증한다.

---

## 9. 새 파일 생성

새 파일은 기존 파일 덮어쓰기 위험이 없지만 다음을 확인한다.

- 같은 역할의 파일이 이미 존재하지 않는가
- 대상 경로와 파일명이 프로젝트 규칙에 맞는가
- 기존 문서 또는 코드에서 참조할 위치가 명확한가
- 생성 직전 대상 브랜치에 같은 경로가 새로 생기지 않았는가

이미 같은 경로가 존재하면 create 작업을 update로 임의 전환하지 않는다.

---

## 10. 파일 삭제

파일 삭제는 수정보다 보수적으로 처리한다.

삭제 전 다음을 확인한다.

- 최신 SHA
- 다른 문서 또는 코드의 참조 여부
- archive 대상인지 실제 삭제 대상인지
- 사용자가 삭제 범위를 명시했는지

삭제 직전 SHA가 최초 확인 SHA와 달라졌다면 자동 삭제하지 않고 중단한다.

---

## 11. 대규모 문서 정리

기존 문서가 많을 때 동일한 규칙을 모든 파일에 복사하지 않는다.

가능하면 다음 구조를 사용한다.

```text
중앙 정책 문서
→ 상위 가이드라인에서 참조
→ 기능별 문서는 필요한 경우에만 참조
```

기존 문서 전체를 한 번에 마이그레이션하기보다 다음 방식을 우선한다.

```text
중앙 정책 도입
→ 명시적 충돌 문서 탐색
→ 충돌 문서만 최소 수정
→ 나머지는 touch-on-change 방식으로 점진 정리
```

archive 또는 과거 버전 문서는 현재 동작 기준으로 다시 쓰지 않는다.

---

## 12. GitHub Connector의 기술적 한계와 해석

현재 GitHub Connector의 기존 파일 업데이트는 최종적으로 완성된 파일 전체 내용과 현재 blob SHA를 전달하는 방식이다.

따라서 Patch-first는 GitHub API 자체의 patch 옵션을 의미하지 않는다.

Patch-first는 다음을 의미한다.

> 변경 의도와 생성 과정은 최소 diff를 기준으로 관리하고, 최신 파일에 해당 변경만 적용한 결과를 검증한 뒤, 최종 단계에서만 완성된 전체 파일을 GitHub에 기록한다.

즉 다음 둘을 구분한다.

```text
변경 설계 단위
= patch / diff

최종 GitHub 전송 단위
= 검증된 완성 파일 전체 내용
```

---

## 13. 중단 조건

다음 조건에서는 자동 쓰기를 중단하고 사용자에게 보고한다.

- 쓰기 직전 파일이 예상과 다르게 변경되었고 변경 구간이 겹침
- patch context가 최신본과 일치하지 않음
- 대상 브랜치가 예상과 다름
- 기능별 확정안 또는 최신 코드와 충돌 발견
- 변경 목적을 만족하려면 범위 밖 파일까지 수정해야 함
- 파일 전체 재작성 없이는 안전하게 수정할 수 없지만 전면 개편이 사용자에게 승인되지 않음

중단은 실패가 아니라 최신 변경을 보존하기 위한 정상적인 안전 절차로 취급한다.

---

## 14. 완료 보고

GitHub 쓰기 완료 시 필요 범위에서 다음을 보고한다.

- 대상 브랜치
- 변경 파일
- 변경 목적
- 충돌 여부
- 최신본 재확인 여부
- 예상 외 변경 여부
- 생성된 commit 또는 PR

단순 파일 수정 작업에서 불필요하게 긴 로그 전체를 나열하지 않는다.

---

## 15. 요약

Trend Leader의 GitHub 파일 수정 기본 원칙은 다음 한 줄로 정리한다.

> **최신본을 기준으로 최소 변경을 설계하고, 쓰기 직전 다시 검증하며, 충돌이 없을 때만 최신본에 변경을 적용한다.**

핵심 절차:

```text
Latest Read
→ Minimal Diff
→ Re-read Before Write
→ SHA/Context Check
→ Apply to Latest
→ Diff Review
→ Write with Latest SHA
```
