# Trend Leader AI Development Guidelines

> 문서 버전: v1.0  
> 작성 기준일: 2026-09-02  
> 적용 대상: Trend Leader의 설계, 구현, 코드 리뷰, 테스트, 문서화 및 완료 검증  
> 문서 역할: 프로젝트 지침을 보완하는 상세 실행 기준

---

## 0. 문서 목적

이 문서는 Trend Leader에서 AI와 함께 개발할 때 다음 문제를 방지하기 위한 전역 가이드라인이다.

- 실제 코드와 다른 내용을 기억이나 추측으로 구현하는 문제
- 기능 범위를 정하지 않은 채 즉흥적으로 코드를 늘리는 문제
- 코드 작성 완료를 기능 완료로 오해하는 문제
- 이미 확정된 설계와 API 계약을 조용히 변경하는 문제
- 테스트의 목적 없이 테스트 개수만 늘리는 문제
- Backend, Frontend, Database의 계약이 서로 어긋나는 문제
- 현재 버전과 맞지 않는 기술 정보를 사실처럼 적용하는 문제

Trend Leader의 기본 개발 흐름은 다음과 같다.

```text
문제 정의
→ 현재 상태 확인
→ 범위와 계약 확정
→ 설계
→ 테스트 전략 결정
→ 구현
→ 자동 테스트
→ 실제 동작 검증
→ 회귀 검증
→ 문서 및 커밋 전 최종 점검
```

코드 생성 속도보다 **설계 의도, 검증 가능성, 변경 안전성**을 우선한다.

## 1. 기준 문서와 우선순위

### 1.1 판단 우선순위

서로 다른 자료가 충돌하면 다음 순서로 판단한다.

1. 현재 채팅에서 사용자가 명시한 범위와 결정
2. 해당 기능의 최신 설계 확정안
3. 동결된 스키마 결정 문서와 명시적인 API 계약
4. 이 가이드라인
5. 현재 대상 브랜치의 실제 코드와 테스트가 보여 주는 구현 상태
6. README, 기능 명세서, 초기 기획서 등 일반 참고 문서
7. 과거 대화의 기억 또는 이전 답변

단, 이 우선순위는 상위 문서의 내용을 무조건 코드에 덮어쓰라는 뜻이 아니다.

- 실제 코드는 **현재 구현 상태의 사실**이다.
- 설계 확정안은 **의도한 목표 상태의 기준**이다.
- 둘이 충돌하면 충돌을 먼저 보고하고, 오래된 문서인지 미완성 구현인지 판별한 뒤 진행한다.

### 1.2 충돌 처리

충돌을 발견하면 조용히 한쪽을 선택하지 않는다.

```text
충돌한 항목
→ 각 자료가 말하는 내용
→ 실제 코드 영향 범위
→ 유지 가능한 기존 설계
→ 변경이 필요할 경우 대안과 트레이드오프
→ 사용자 확인 또는 이미 정해진 우선순위에 따른 결정
```

기능별 설계 확정안이 이 문서보다 구체적이면 기능별 확정안을 우선한다. 이 경우 어떤 전역 원칙이 구체화되거나 예외 처리되었는지 알린다.

### 1.3 문서의 시간성

설계 문서에 기록된 커밋 SHA와 버전은 설계 당시의 기준점이다. 이를 현재 상태로 간주하지 않는다.

- 구현 시작 시 대상 브랜치의 최신 HEAD를 다시 확인한다.
- 문서 작성 이후 변경된 Router, Service, Repository, Schema, Dependency, Test, Frontend 호출부를 확인한다.
- 과거에 통과한 테스트 결과를 현재도 통과한다고 가정하지 않는다.

## 2. 작업 범위와 변경 통제

### 2.1 채팅 및 작업 단위

복잡한 기능은 가능하면 다음 단위로 분리한다.

1. 설계 채팅: 문제, 범위, 정책, API 계약, 데이터 흐름, 테스트 전략 확정
2. 구현 채팅: 확정안을 기준으로 단계별 코드 변경과 검증
3. 필요 시 별도 후속 작업: 리팩터링, 인프라 고도화, 성능 개선, 범위 밖 보안 강화

설계 채팅에서는 구현을 서두르지 않고 미확정 정책을 드러낸다. 구현 채팅에서는 확정된 정책을 다시 처음부터 재설계하지 않되, 현재 코드와 충돌하면 진행을 멈추고 충돌부터 해결한다.

### 2.2 범위 고정

작업을 시작할 때 최소한 다음을 명확히 한다.

- 해결하려는 사용자 또는 시스템 문제
- 포함 범위
- 제외 범위
- 성공 조건
- 영향을 받는 계층과 파일
- 기존 기능 중 반드시 보존해야 하는 동작

정확성에 영향을 주지 않는 사소한 모호함은 합리적으로 해석해 진행할 수 있다. 다음처럼 결과가 크게 달라지는 정보가 없으면 추측하지 않는다.

- 대상 브랜치 또는 코드 버전
- 인증 필요 여부
- 데이터 영속화 및 삭제 정책
- API 요청·응답 계약
- Transaction 경계
- 하위 호환성 요구
- 외부 서비스나 라이브러리의 실제 버전

### 2.3 범위 밖 발견 사항

작업 중 발견한 문제는 다음 중 하나로 분류한다.

- 현재 기능을 막는 결함: 현재 범위에서 처리
- 현재 변경으로 생기는 회귀 위험: 현재 범위에서 방어
- 관련 있지만 독립적인 개선: 제안 사항으로 분리
- 대규모 구조 변경: 별도 설계 작업으로 분리

범위 밖 개선을 유용하다는 이유만으로 함께 구현하지 않는다.

## 3. 현재 코드 검증 원칙

### 3.1 기준 브랜치

- 사용자가 브랜치를 지정하면 해당 브랜치의 최신 HEAD를 기준으로 한다.
- 지정이 없으면 기본적으로 `dev` 최신 HEAD를 기준으로 한다.
- 기능 브랜치가 언급되었거나 작업 문맥상 명백하면 해당 기능 브랜치를 우선 확인하되, 기준을 답변에 명시한다.
- 로컬 작업 트리가 변경되어 있으면 사용자 변경을 보존하고, 관련 변경인지 확인한다.

### 3.2 시작 전 최소 확인

현재 상태가 판단에 영향을 주는 작업에서는 다음을 확인한다.

```text
branch / HEAD / working tree
→ 관련 파일과 최근 변경
→ 호출 및 의존 관계
→ 관련 테스트
→ 프로젝트 버전과 실행 설정
→ 설계 확정안과의 차이
```

파일명만 보고 구현 여부를 판단하지 않는다. 실제 정의와 호출부를 함께 확인한다.

### 3.3 연결 관계 확인 범위

Backend 기능은 필요 범위에서 다음 연결을 추적한다.

```text
Router
→ Dependency
→ Request/Response Schema
→ Service
→ Repository
→ ORM Model / DB Constraint
→ Exception Handler
→ Test
```

Frontend 기능은 필요 범위에서 다음 연결을 추적한다.

```text
Screen / Component
→ Hook
→ API Function
→ API Client
→ Type
→ Provider / Cache / Storage
→ Navigation
→ Test
```

API 변경은 Backend와 Frontend 중 한쪽만 보고 완료 판정하지 않는다.

### 3.4 추측 금지

다음을 확인하지 않은 상태로 만들어 내지 않는다.

- 존재하지 않는 함수, 타입, API, 옵션, 환경변수
- 설치 여부가 확인되지 않은 패키지
- 프로젝트 버전과 맞는지 확인되지 않은 문법
- 보이지 않는 의존 코드의 반환값이나 예외
- DB에 존재한다고 확인되지 않은 컬럼, 인덱스, 제약
- 실제로 실행하지 않은 테스트 결과

확정할 수 없는 부분은 `추가 확인 필요`로 분리하고, 확정을 위해 필요한 파일이나 정보를 구체적으로 적는다.

## 4. 문제와 설계의 구조화

### 4.1 구현 전에 답해야 할 질문

기능 구현 전에 최소한 다음을 검토한다.

1. 이 기능이 해결하는 문제는 무엇인가?
2. 핵심 비즈니스 규칙은 무엇인가?
3. 규칙을 어느 계층이 소유해야 하는가?
4. 정상 경로 외에 어떤 실패 경로가 있는가?
5. 동시 요청, 중복 요청, 재시도에서 무슨 일이 생기는가?
6. Backend와 Frontend가 합의해야 할 계약은 무엇인가?
7. 어떤 테스트가 실패하면 이 기능이 깨졌다고 말할 수 있는가?
8. 실제 사용 환경에서 자동 테스트만으로 확인할 수 없는 부분은 무엇인가?

### 4.2 대안 비교

의미 있는 설계 선택지가 둘 이상일 때는 최소 두 대안을 비교한다.

| 비교 항목 | 확인 내용 |
| --- | --- |
| 책임 위치 | 어느 계층이 판단을 소유하는가 |
| 정확성 | 실패·동시성 상황에서도 규칙이 유지되는가 |
| 복잡도 | 현재 MVP에 필요한 복잡도인가 |
| 테스트 가능성 | 규칙을 고립해 검증할 수 있는가 |
| 유지보수성 | 다음 기능이 추가될 때 변경 범위가 어디까지인가 |
| 기존 구조 적합성 | 현재 Trend Leader 패턴과 일치하는가 |

선택지가 실질적으로 하나뿐이면 형식적인 대안을 억지로 만들지 않는다.

### 4.3 DDD 적용 수준

Trend Leader에서는 DDD 용어와 패턴을 기계적으로 늘리지 않고, 다음 목적에 한해 실용적으로 적용한다.

- 비즈니스 규칙을 UI, Router, SQL 세부 구현과 분리
- 도메인 상태 전이와 불변조건을 Service에서 명확히 표현
- Repository를 영속성 접근 경계로 유지
- 도메인 충돌을 HTTP나 DB 예외 문자열이 아닌 의미 있는 오류로 번역
- 기능 간 책임과 변경 이유를 설명할 수 있게 유지

Aggregate, Domain Event, Value Object 같은 패턴은 실제 복잡성을 줄일 때만 도입한다. 작은 CRUD에 형식적으로 추가하지 않는다.

## 5. 계층별 책임

### 5.1 Backend 기본 흐름

```text
Client → Router → Service → Repository → Database
```

#### Router

- HTTP 요청 수신과 응답 반환
- Dependency를 통한 인증 사용자 또는 공통 자원 주입
- Request/Response Schema 연결
- 성공 상태 코드와 공개 API 계약 선언
- Service의 도메인 결과를 공통 응답 구조로 반환

Router에 핵심 비즈니스 판단, 직접 SQL, 여러 단계 Transaction 로직을 넣지 않는다.

#### Service

- 유스케이스 조정
- 비즈니스 규칙과 상태 전이 검증
- 여러 Repository 작업의 순서 결정
- Transaction 경계 소유
- DB 제약 예외를 도메인 충돌로 번역
- 필요한 경우 제한된 전체 Transaction 재시도 조정

Service가 모든 코드를 모으는 거대한 클래스가 되지 않도록, 독립된 정책이나 순수 변환은 별도 책임으로 분리할 수 있다.

#### Repository

- 데이터 조회, 저장, 수정, 삭제
- ORM Query 캡슐화
- Service가 의도를 표현할 수 있는 메서드 제공
- 필요 시 `flush()`를 통해 DB 제약을 Transaction 내부에서 드러냄

Repository는 HTTP 상태 코드, 화면 이동, 사용자 메시지를 알지 않는다. 기본 정책상 최종 `commit()`과 업무 재시도를 소유하지 않는다. 기능별 확정안이 다르게 정하면 그 문서를 따른다.

#### Schema

- 요청 형태, 타입, 길이, 형식 같은 API 경계 검증
- 응답 계약 명시
- DB Model을 그대로 외부 계약으로 노출하지 않음

Schema Validation과 도메인 Validation을 구분한다.

```text
형식·타입·길이 오류 → Schema / 422
현재 상태·중복·업무 규칙 충돌 → Service / Domain Error
```

#### Dependency

- 인증, DB Session, 공통 요청 의존성 제공
- Router와 함께 API 경계에 위치
- DTO나 비즈니스 Service의 대체물로 사용하지 않음

### 5.2 Frontend 기본 흐름

```text
User → Screen → Hook → API Function → API Client → Backend
```

#### Screen

- 화면 구성과 사용자 입력
- 로딩, 실패, 빈 상태, 재시도 UX
- 화면 수준 Navigation 이벤트

Screen에서 Axios 요청, Token 처리, Query Cache 조작 규칙을 직접 중복 구현하지 않는다.

#### Hook

- TanStack Query 기반 Server State 연결
- Mutation 수명 주기와 Query 무효화 또는 Cache 갱신
- Screen이 사용하기 쉬운 상태와 명령 제공

#### API Function

- Endpoint, Method, 요청값, 응답값 연결
- 공개 API와 인증 API에 맞는 Client 선택
- 화면 정책이나 Navigation 판단을 포함하지 않음

#### Provider

- 여러 화면이 공유해야 하는 앱 수준 상태와 수명 주기 관리
- 인증의 경우 현재 확정된 `AuthProvider` 중심 구조 유지

#### Component

- 재사용 가능한 표현과 상호작용
- 특정 화면의 Server State 조정 책임을 불필요하게 흡수하지 않음

### 5.3 공통 코드 배치

- 둘 이상의 기능이 실제로 공유하면 `shared`를 검토한다.
- 특정 기능에만 필요한 코드는 해당 `features` 내부에 둔다.
- 미래에 쓸 가능성만으로 추상화하거나 빈 폴더를 미리 만들지 않는다.
- 중복 한 번보다 잘못된 공통 추상화의 비용이 더 클 수 있음을 고려한다.

## 6. API 계약 원칙

### 6.1 계약 구성 요소

API는 최소한 다음 항목을 함께 확정한다.

- Method와 Endpoint
- 인증 필요 여부와 Frontend API Client
- Path, Query, Body 필드와 Validation
- 성공 상태 코드와 응답 구조
- 실제 발생 가능한 오류 상태 코드
- machine-readable 오류 데이터
- Frontend의 성공·실패 처리
- Transaction과 동시성 정책

### 6.2 공통 응답 구조

현재 프로젝트의 공통 응답 구조를 유지한다.

```json
{
  "success": true,
  "statusCode": 200,
  "message": "요청에 성공했습니다.",
  "data": {}
}
```

기존 코드와 기능별 확정안이 정의한 필드명을 임의로 바꾸지 않는다.

### 6.3 오류 계약

- 모든 Endpoint에 가능한 상태 코드를 기계적으로 복사하지 않는다.
- 해당 Endpoint에서 실제로 발생할 수 있는 오류만 문서화하고 테스트한다.
- Frontend 분기가 필요하면 사용자용 `message` 문자열보다 `reason`, `field` 등 machine-readable 데이터를 사용한다.
- 401, 403, 404, 409, 422의 의미를 섞지 않는다.
- 공통 Exception Handler가 런타임 응답을 만든다는 사실과 OpenAPI에 문서화되었다는 사실을 구분한다.
- 공개 계약으로 확정한 오류가 실제 응답, API 명세, 테스트에서 일치하는지 확인한다.

### 6.4 계약 변경 절차

기존 API 계약 변경 시 다음 영향 범위를 함께 확인한다.

```text
Backend Schema / Router / Service
↔ Exception Handler / OpenAPI
↔ Frontend Type / API Function / Hook / Screen
↔ 자동 테스트 / 실제 기기 시나리오
↔ API 명세 문서
```

Backend만 먼저 바꾸고 Frontend 불일치를 후속으로 숨겨 두지 않는다. 단계적 구현이 필요하면 중간 상태와 다음 단계를 명시한다.

## 7. Database와 Transaction 원칙

### 7.1 스키마 기준

- 동결된 `schema_decisions.md`, 최신 ORM Model, Alembic Migration의 관계를 확인한다.
- SQL 파일과 ERD 이미지는 참고 또는 검증 자료일 수 있으므로, 현재 실행 스키마의 유일한 근거라고 단정하지 않는다.
- 스키마 변경은 Model만 수정하지 않고 Migration과 제약·인덱스 영향을 함께 다룬다.
- 이미 적용된 Migration 파일을 임의로 다시 쓰기보다 새 Migration이 필요한지 판단한다.

### 7.2 Application Validation과 DB Constraint

둘은 경쟁 관계가 아니라 서로 다른 방어선이다.

```text
사전 조회 / Service Validation
→ 빠르고 이해하기 쉬운 사용자 피드백

DB UNIQUE / FK / NOT NULL 등
→ 동시 요청까지 포함한 최종 무결성 방어
```

사전 중복 확인만으로 Race Condition이 해결되었다고 판단하지 않는다.

### 7.3 Transaction 경계

- 하나의 유스케이스에서 함께 성공하거나 함께 실패해야 하는 변경을 한 Transaction으로 묶는다.
- 기본적으로 Service가 `commit()`과 `rollback()`을 조정한다.
- `IntegrityError` 등 DB 예외가 발생하면 Session 상태를 정상화하기 위해 필요한 rollback을 먼저 수행한 뒤 도메인 예외로 번역한다.
- 넓은 예외 포착으로 모든 DB 오류를 동일한 중복 오류로 바꾸지 않는다.
- 원래 예외를 보존하면서 사용자에게 노출할 안전한 오류만 변환한다.

### 7.4 동시성과 재시도

동시성 위험이 있는 기능에서는 다음을 검토한다.

- 중복 요청의 최종 결과
- Lost Update 가능성
- Idempotency 필요 여부
- UNIQUE 또는 Lock 필요 여부
- 낙관적·비관적 동시성 제어 필요 여부
- 재시도 가능한 일시 오류와 재시도하면 안 되는 업무 오류

재시도는 일반 해결책이 아니다.

- 기능별 확정안에서 정한 오류에만 적용한다.
- 횟수는 제한한다.
- 부분 Query가 아니라 전체 Transaction을 처음부터 다시 실행한다.
- 재시도 사이의 Session 상태와 rollback을 보장한다.
- 실패를 감추거나 무한 반복하지 않는다.

특정 기능에서 확정한 MariaDB 오류 대응을 다른 기능에 자동으로 일반화하지 않는다.

## 8. 인증과 보안 원칙

### 8.1 보안 경계

- Backend의 인증·인가 검증이 최종 보안 경계다.
- Frontend Auth State와 Navigation 분기는 UX 제어이며 권한 검증의 대체물이 아니다.
- 보호 API는 공통 인증 Dependency를 사용하고 사용자 존재 및 상태 정책을 일관되게 적용한다.

### 8.2 Frontend 인증 구조

현재 확정된 구조를 유지한다.

```text
SecureStore
→ AuthProvider
→ RootNavigator
→ Screen
```

- 영속 Token과 현재 앱의 인증 상태를 같은 개념으로 취급하지 않는다.
- Public API와 Authenticated API Client를 구분한다.
- 공통 401 처리는 인증 요청에만 적용한다.
- 오래된 요청의 401이 새 로그인 세션을 종료하지 않도록 요청 Token과 현재 Token의 관계를 확인한다.
- 동시 401 Cleanup은 한 번만 실행되도록 방어한다.
- 사용자 전환 또는 로그아웃 시 인증 사용자에 종속된 Query Cache를 정리한다.

기능별 인증 확정안이 변경되기 전까지 Refresh Token이나 서버 측 Token Revocation을 존재한다고 가정하지 않는다.

### 8.3 비밀정보 보호

다음을 코드, 로그, 테스트 출력, 문서 예시에 노출하지 않는다.

- 실제 비밀번호와 Password Hash
- JWT 원문과 Secret
- DB Password
- 외부 API Key
- 개인 식별 정보가 포함된 실제 운영 데이터

클라이언트 환경변수에는 서버 비밀값을 넣지 않는다. 실제 `.env`는 Git에 포함하지 않고 `.env.example`에는 안전한 예시만 둔다.

### 8.4 보안 검토 범위

기능에 관련된 범위에서 다음을 확인한다.

- 인증과 인가의 구분
- 수평 권한 상승 가능성
- 입력 검증과 정보 노출
- Token 및 Cache 정리
- 오류 메시지를 통한 계정 존재 여부 노출
- 비밀번호 처리와 로그 금지
- 민감 데이터의 저장 위치

현재 MVP 범위를 넘어서는 보안 고도화는 위험과 우선순위를 설명하고 후속 작업으로 분리한다.

## 9. Frontend 상태와 비동기 흐름

### 9.1 상태 구분

다음을 가능한 한 구분한다.

- Server State: API가 소유하며 Query가 관리하는 상태
- Draft State: 사용자가 저장 전 편집 중인 로컬 상태
- App State: 인증처럼 여러 화면의 흐름을 결정하는 상태
- Persistent State: SecureStore 등 앱 재실행 후 복원할 데이터
- Navigation State: 현재 화면 흐름을 나타내는 UX 상태

Server State를 로컬 State에 무조건 복사하거나, Draft를 Background Refetch 때마다 덮어쓰지 않는다.

### 9.2 TanStack Query

- Query Key는 일관되게 관리한다.
- Mutation 성공 후 `setQueryData`, `invalidateQueries`, 재조회 중 어느 방식이 계약에 맞는지 결정한다.
- Cache 갱신과 Auth State 갱신의 책임을 구분한다.
- 비동기 Callback의 Promise 처리 여부는 현재 설치 버전과 공식 문서를 확인한 뒤 판단한다.
- 로딩, 오류, 빈 데이터, 재시도 상태를 Screen UX에 반영한다.

### 9.3 비동기 Race Condition

다음 상황을 검토한다.

- 이전 요청이 새 상태보다 늦게 완료됨
- 화면 이탈 후 Callback 실행
- 중복 탭 또는 중복 Mutation
- 로그인 전 요청의 오류가 로그인 후 도착
- Background Refetch가 사용자 Draft를 덮어씀

단순히 `await`를 추가했다는 이유만으로 Race Condition이 해결되었다고 단정하지 않는다. 상태 식별자, 요청 시점, 취소 또는 무시 정책을 함께 본다.

## 10. TDD 적용 정책

### 10.1 도입 방향

Trend Leader는 기존 전체 코드를 한 번에 TDD 방식으로 다시 작성하지 않는다. 다음 작업부터 점진적으로 적용한다.

- 신규 Backend 비즈니스 규칙
- 기존 Service 동작 변경
- 재발 방지가 필요한 버그 수정
- Transaction, 중복, 상태 전이처럼 실패 비용이 큰 로직
- 입력과 결과를 명확하게 정의할 수 있는 순수 로직

기존 기능을 수정할 때 안전망이 부족하면 먼저 현재 동작을 고정하는 특성 테스트 또는 회귀 테스트를 추가한다.

### 10.2 TDD 적합성 판단

#### 우선 적용

- Service의 분기와 불변조건
- 상태 전이
- 권한 규칙
- 정규화와 계산
- 중복 및 충돌 처리
- 버그 재현이 가능한 문제

#### 선택 적용

- Router의 얇은 연결 코드
- Repository의 단순 Query
- Frontend Hook과 Provider의 상태 전이
- 사용자 입력에 따른 Screen 동작

이 경우 계약 또는 상호작용 실패 위험이 충분한지 보고 결정한다.

#### 강제하지 않음

- 문서만 변경
- 자동 생성 파일 자체
- 동작 변화가 없는 기계적 이름 변경
- 기존 패턴을 그대로 복제하는 매우 얇은 배선 코드

단, 이런 변경도 회귀 위험이 있으면 기존 테스트와 정적 검사를 실행한다. TDD를 적용하지 않는 경우에는 그 이유와 대신 사용할 검증 방법을 짧게 밝힌다.

### 10.3 Red → Green → Refactor

#### 1단계: Red

- 요구사항 하나를 관찰 가능한 행동으로 표현한다.
- 그 행동이 아직 없기 때문에 실패하는 최소 테스트를 작성한다.
- 테스트가 의도한 이유로 실패하는지 직접 확인한다.
- Import 오류, Fixture 오류, 잘못된 Mock 때문에 실패한 상태를 Red 완료로 보지 않는다.

#### 2단계: Green

- 현재 실패 테스트를 통과시키는 최소 구현을 한다.
- 미래 요구사항을 미리 추측해 확장하지 않는다.
- 관련 테스트를 실행해 새 테스트가 실제로 통과하는지 확인한다.

#### 3단계: Refactor

- 중복, 이름, 책임, 가독성을 개선한다.
- 동작을 바꾸지 않는다.
- 리팩터링 후 관련 테스트를 다시 실행한다.

작은 규칙 단위로 이 순환을 반복하고, Phase가 끝나면 넓은 회귀 테스트를 실행한다.

### 10.4 테스트를 먼저 확정할 때 기록할 내용

```text
행동 이름
Given: 시작 상태와 입력
When: 실행할 유스케이스
Then: 관찰할 결과와 부수 효과
테스트 수준: Unit / Integration / Contract / UI / Acceptance
이 테스트가 막는 회귀
```

테스트가 내부 구현 순서를 지나치게 고정하지 않도록 결과와 계약을 중심으로 작성한다.

### 10.5 버그 수정 규칙

재현 가능한 버그는 기본적으로 다음 순서를 따른다.

```text
버그 재현
→ 원인 가설
→ 실패하는 회귀 테스트
→ 최소 수정
→ 회귀 테스트 통과
→ 관련 전체 테스트
→ 실제 재현 절차 재검증
```

테스트로 재현하기 어려우면 그 이유를 밝히고 로그, 수동 시나리오, 정적 분석 등 대체 검증을 사용한다.

## 11. 테스트 설계

### 11.1 테스트 수준별 목적

| 수준 | 주된 목적 | 대표 대상 |
| --- | --- | --- |
| Unit | 규칙과 분기를 빠르게 고립 검증 | Service, 순수 함수, 상태 Reducer |
| Repository Integration | 실제 ORM Query와 DB 동작 검증 | UNIQUE, FK, flush, transaction |
| Service Integration | 여러 계층과 Transaction의 협력 검증 | 저장·수정 유스케이스 |
| Router / Contract | HTTP 경계와 공개 계약 검증 | status, schema, auth, envelope |
| Frontend Unit / Integration | Hook, Provider, Screen 상호작용 검증 | cache, 상태 전이, 오류 UX |
| Acceptance | 실제 실행 환경의 전체 흐름 확인 | Expo 기기, 실제 Backend 연결 |

모든 기능에 모든 수준의 테스트를 동일한 개수로 강제하지 않는다. 실패 위험이 존재하는 가장 낮고 빠른 수준을 우선하고, 실제 통합 동작이 핵심이면 통합 테스트를 추가한다.

### 11.2 Mock 사용

- 외부 경계나 다른 계층을 고립할 목적이 있을 때 사용한다.
- Mock의 호출 횟수보다 중요한 도메인 결과와 부수 효과를 우선 검증한다.
- SQLAlchemy, MariaDB 제약, Axios Interceptor처럼 실제 동작이 검증 대상이면 Mock만으로 완료하지 않는다.
- Mock이 실제 인터페이스와 어긋나지 않도록 현재 시그니처를 확인한다.

### 11.3 Backend 최소 검토 항목

- 정상 결과
- Schema Validation
- 인증 실패와 권한 실패
- 존재하지 않는 리소스
- 중복 또는 상태 충돌
- commit / rollback
- DB Constraint 위반
- 동시성 또는 재시도 정책
- 응답 계약

해당 기능에 존재하지 않는 경우는 억지로 테스트하지 않는다.

### 11.4 Frontend 최소 검토 항목

- 로딩
- 성공
- Validation 오류
- Domain 오류
- Network / 5xx
- 중복 실행 방지
- Cache 갱신
- Auth State 영향
- Navigation 결과
- 오래된 비동기 응답

### 11.5 테스트 품질

좋은 테스트는 다음 성질을 가진다.

- 실패 이유가 하나의 행동과 연결된다.
- 테스트 이름이 업무 규칙을 설명한다.
- 실행 순서와 외부 상태에 과도하게 의존하지 않는다.
- 다른 테스트와 데이터를 공유해 우연히 통과하지 않는다.
- 구현을 리팩터링해도 계약이 같으면 유지된다.
- 실패 메시지로 원인을 추적할 수 있다.

테스트 수나 커버리지 숫자만으로 품질을 판정하지 않는다.

## 12. 구현 원칙

### 12.1 최소 변경

- 현재 요구사항을 충족하는 가장 작은 일관된 변경을 우선한다.
- 관련 없는 포맷 변경이나 대규모 이름 변경을 섞지 않는다.
- 기존 사용자 변경과 무관한 파일을 되돌리지 않는다.
- 새 추상화는 두 개 이상의 실제 책임을 줄이거나 중요한 정책을 표현할 때 도입한다.

### 12.2 적용 가능한 코드

코드를 제시하거나 수정할 때는 현재 프로젝트에 바로 적용 가능한 형태를 우선한다.

- 정확한 파일 위치와 책임을 밝힌다.
- 필요한 import와 타입을 현재 코드에서 확인한다.
- 일부 코드만 확정 가능하면 그 범위만 작성한다.
- 생략 부호가 들어간 예시를 완성 코드처럼 제시하지 않는다.
- Migration, 환경변수, 패키지 변경이 필요하면 함께 명시한다.

### 12.3 주석과 이름

- 이름으로 의도가 드러나면 설명형 주석을 반복하지 않는다.
- 왜 필요한지 코드만으로 알기 어려운 정책, Race 방어, 보안 전제에 주석을 사용한다.
- 현재 구현이 무엇을 하는지보다 그 선택의 이유와 유지해야 할 불변조건을 기록한다.
- 오래되기 쉬운 장문의 주석은 테스트 이름이나 설계 문서로 이동한다.

### 12.4 리팩터링

리팩터링은 동작 보존 변경이다.

- 먼저 관련 테스트 또는 특성 테스트로 현재 동작을 고정한다.
- 구조 변경과 기능 변경을 가능한 한 분리한다.
- 책임 이동 시 호출부, 테스트, 문서를 함께 갱신한다.
- 단순히 파일을 나누는 것을 책임 분리 완료로 판단하지 않는다.

## 13. 검증과 완료 판정

### 13.1 단계별 검증

```text
변경 파일 정적 확인
→ 가장 가까운 단위 테스트
→ 관련 통합·계약 테스트
→ Backend 또는 Frontend 관련 전체 테스트
→ Type Check / Lint / Format
→ 실제 실행 또는 기기 시나리오
→ Git diff / working tree 최종 확인
```

프로젝트에 실제로 존재하는 명령과 설정만 사용한다. 운영체제와 Shell 차이를 고려하며, Bash의 줄 연속 문자 `\`와 PowerShell의 백틱 등 서로 다른 문법을 섞지 않는다.

### 13.2 결과 보고

- 실행한 명령과 결과를 구분한다.
- 통과 개수와 실패 개수를 실제 출력 기준으로 보고한다.
- 일부 테스트만 실행했으면 전체 회귀가 통과했다고 표현하지 않는다.
- 실행하지 못한 검증은 이유와 남은 위험을 적는다.
- 경고를 실패와 같게 취급하지 않되, 무시 가능한지 근거를 확인한다.

### 13.3 기능 완료 기준

다음이 모두 충족되어야 기능 완료로 판단한다.

- 범위 내 요구사항 구현
- 설계 확정안과 코드 일치
- Backend ↔ Frontend 계약 일치
- 정상 및 핵심 실패 경로 검증
- 관련 자동 테스트 통과
- 필요한 실제 동작 또는 기기 Acceptance Test 통과
- 보안과 동시성 위험 검토
- 문서와 예시가 현재 동작과 일치
- 회귀 검증 완료
- 의도하지 않은 변경 없음

코드가 작성되었거나 특정 테스트 하나가 통과했다는 사실만으로 완료라고 말하지 않는다.

### 13.4 완료 상태 표현

작업 결과는 필요에 따라 다음처럼 구분한다.

- 구현 완료: 코드 변경이 끝남
- 자동 검증 완료: 정해진 자동 테스트와 정적 검사 통과
- 실제 동작 검증 완료: 서버, Swagger, 기기 등 실제 환경 확인
- 기능 완료: 확정된 완료 기준 전체 충족
- 추가 검증 필요: 일부 증거가 없어 완료 판정 보류

### 14.1 현재성 있는 정보

다음은 기억만으로 강하게 단정하지 않는다.

가능하면 다음 순서로 검증한다.

1. 현재 프로젝트에 설치된 버전과 설정
2. 해당 버전의 공식 문서
3. 공식 저장소의 코드, 릴리스 노트, 이슈
4. 표준 문서 또는 신뢰할 수 있는 1차 자료
5. 보조 설명 자료

### 14.2 표현의 강도

다음을 구분한다.

- 동작한다: 현재 환경이나 공식 동작으로 확인됨
- 지원한다: 공식 지원 범위가 확인됨
- 권장한다: 공식 권고 또는 설계상 권고이며 근거를 밝힘
- 가능하다: 기술적으로 할 수 있으나 권장 여부는 별도
- 추론이다: 코드나 자료를 바탕으로 한 해석
- 확인되지 않았다: 필요한 증거가 없음

검색 결과 제목이나 요약문만으로 중요한 기술적 사실을 확정하지 않는다. 원문에서 해당 주장을 직접 확인한다.

### 14.3 이전 답변 정정

이전 답변이 현재 코드, 실행 결과, 공식 자료와 충돌하면 이전 답변을 유지하려 하지 않는다.

```text
이전 설명 중 잘못되거나 오래된 부분
→ 새로 확인한 근거
→ 수정된 결론
→ 현재 작업에 미치는 영향
```

순서로 명확히 바로잡는다.

## 16. Git 및 협업 원칙

### 16.1 변경 전

- 관련 변경과 사용자 작업 구분
- 대상 기능의 최신 확정안 확인

### 16.2 변경 후

- `git diff`로 의도한 변경만 포함되었는지 확인
- 생성 파일과 삭제 파일 확인
- Secret 또는 실제 `.env` 포함 여부 확인
- 테스트 결과 확인
- 필요 시 문서 변경 포함

### 16.3 Commit과 Push

- Commit과 Push는 사용자가 요청했거나 명시적으로 합의한 범위에서 수행한다.
- 검증되지 않은 상태를 완료 커밋으로 만들지 않는다.
- 하나의 Commit에는 설명 가능한 하나의 작업 의도를 유지한다.
- Commit 메시지는 실제 변경 종류와 내용을 반영한다.

## 17. AI 답변 및 협업 방식

### 17.1 결과 중심 보고

먼저 현재 결론과 작업 상태를 말하고, 그 뒤에 근거와 세부 내용을 설명한다.

검토 결과는 가능하면 다음을 구분한다.

- 확인 완료: 실제 코드, 테스트, 문서 또는 공식 자료로 확인
- 설계 판단: 여러 선택지 중 현재 프로젝트에 적합하다고 판단
- 추가 검증 필요: 증거가 부족해 확정 불가
- 제안 사항: 현재 범위 밖이거나 선택 가능한 개선

### 17.2 설명 방식

새 개념은 다음 순서로 설명한다.

```text
왜 필요한가
→ 어떤 문제를 해결하는가
→ Trend Leader의 어느 흐름에 적용되는가
→ 코드와 테스트에서는 어떻게 표현되는가
```

기술적 사실, 프로젝트 설계 권고, 개인적 선호를 가능한 한 구분한다.

### 17.3 질문 사용

- 정확성에 영향이 없는 모호함은 합리적으로 해석하고 진행한다.
- 결과를 크게 바꾸는 필수 정보가 없으면 추측하지 않고 짧게 질문한다.
- 구현을 끝낸 뒤 다음 설계 결정을 확장할 가치가 있으면 사고 확장을 위한 질문을 1~2개 제시할 수 있다.
- 이미 확정된 내용을 반복해서 묻지 않는다.

### 17.4 코드 리뷰 보고 순서

코드 리뷰에서는 요약보다 실제 발견 사항을 우선한다.

1. 심각도와 영향
2. 근거 파일과 코드 위치
3. 재현 조건 또는 실패 경로
4. 수정 방향
5. 테스트 누락
6. 남은 가정과 질문

발견 사항이 없으면 무엇을 확인했고 어떤 위험이 남았는지 적는다.

## 19. 핵심 금지 사항

다음을 하지 않는다.

- 실제 코드를 확인하지 않고 과거 대화만으로 구현
- 존재하지 않는 API, 타입, 패키지, 설정 추측
- 확정 설계를 알리지 않고 변경
- Router나 Screen에 비즈니스 규칙 집중
- 사전 중복 조회만으로 동시성 안전하다고 판단
- 모든 DB 오류를 같은 Domain Error로 변환
- 모든 기능에 동일한 테스트 형태 강제
- 실패 이유를 확인하지 않은 Red 단계
- 테스트를 실행하지 않고 통과했다고 보고
- 자동 테스트만으로 실제 기기 검증까지 완료했다고 표현
- 범위 밖 리팩터링을 몰래 포함
- Secret, Token, 비밀번호, 운영 데이터를 로그나 예시에 노출
- 최신 공식 문서라는 이유만으로 현재 설치 버전에도 그대로 적용
- 코드 생성 속도를 위해 설계와 검증 단계를 생략

## 20. 핵심 원칙 요약

```text
현재 코드를 다시 확인한다.
확정된 범위와 설계를 지킨다.
사실과 판단과 미확정을 구분한다.
비즈니스 규칙은 책임 있는 계층에 둔다.
API와 Database Constraint를 함께 설계한다.
신규·변경 규칙은 TDD 적합성을 먼저 판단한다.
버그는 가능한 경우 실패하는 회귀 테스트부터 고친다.
코드 작성, 자동 검증, 실제 검증, 기능 완료를 구분한다.
Backend와 Frontend의 계약이 끝까지 일치하는지 확인한다.
확인되지 않은 내용은 그럴듯하게 채우지 않는다.
```

Trend Leader의 목표는 많은 코드를 빠르게 만드는 것이 아니라, **왜 이 구조가 필요한지 설명할 수 있고 다음 변경에서도 안전하게 검증할 수 있는 시스템을 만드는 것**이다.
