# Google Trends RSS 자동 수집·저장·게시 이용 권한 검토 v0.1

> 문서 상태: Design First Pass / 미동결 / 운영 승인 아님  
> 검토일: 2026-10-30 (KST)  
> 대상: Google Trends Trending now 대한민국 RSS (`https://trends.google.com/trending/rss?geo=KR`)  
> 검토 성격: 기술 PoC와 분리한 외부 데이터 이용 정책 및 운영 가능성 분석  
> 변경 제한: GitHub·Notion·DB·프로젝트 코드 미변경 / RSS P0~P3 FROZEN 계약 보존

## 0. 요약 및 판정 원칙

- Google Trends의 Trending now RSS 내보내기 기능은 **공식 안내가 확인**된다(G-01).
- Google Trends 데이터는 **Google 서비스 약관을 준수하는 범위에서 이용할 수 있고, 재사용 시 출처 인용이 요구**된다(G-02).
- 정기적 서버 자동 요청, 반복 수집, 장기 DB 보관, 제3자 기사 메타데이터 복제, 공개 앱 자동 게시는 **이들 공식 안내만으로 포괄 허용이 확인되지 않는다**.
- Google 일반 서비스 약관에서 기계 판독 지시(`robots.txt` 등)에 위반되는 자동 접근과 제3자 권리 침해를 제한한다(G-03). 이것은 **모든 자동 RSS 요청을 일률적으로 금지한다는 뜻은 아니다**.
- Google APIs 약관 Section 5(e)의 데이터베이스 구축·영구 복제·배포 제한은 적용 대상 API에 중요한 조항이다. 그러나 **해당 RSS 엔드포인트가 Google APIs 약관의 적용 대상이라는 점은 확인되지 않았다**(G-04). 즉, 본 조항을 RSS 금지의 직접 근거로 단정하지 않는다.
- **현재 운영 판정: HOLD.** 합성 XML Fixture 기반 P0~P3 기술 PoC는 이 운영 판정과 별도로 유지한다.

### 구분해야 할 세 가지 권리

1. **접근·수집 권한**: Google Trends RSS 서버에 자동 요청을 보내도 되는가?
2. **Google Trends 데이터 이용 권한**: Google이 제공한 검색어 및 트렌드 신호를 보관·변형·표시해도 되는가?
3. **제3자 언론사 콘텐츠 권한**: RSS에 포함된 원문 기사 제목·본문·이미지·요약 등을 복제하거나 앱에서 표시해도 되는가?

1 또는 2가 허용되더라도 3은 독립적으로 확인한다. 검색어가 일반적 사실에 가까울 수 있다는 추론으로 RSS 데이터베이스 전체 또는 언론사 콘텐츠의 계약상 제한이 제거되지는 않는다.

- Q5. 로고/출처 표기, API 또는 별도 승인, 요청 한도, 권리 주장·삭제 요청 처리 요건은?

### 공식 회신을 받으면 기록할 필드

`received_at`, `sender`, `role_and_authority_verified`, `message_id`, `scope_and_territory`, `auto_fetch_allowed`, `rate_limit`, `retention`, `transformation`, `app_publication`, `third_party_rights`, `commercial_use`, `attribution`, `deletion_and_termination`, `linked_terms`, `unanswered_questions`, `reviewer`, `decision_date`, `decision`.

Google 직원의 일반적 안내를 서면 라이선스와 동일시하지 않는다. 가능하다면 구체적인 RSS URL, 필드 범위, 개발·시연·공개·상업 목적과 허가 주체를 회신에 명시하도록 재확인한다.

## 4. 회신 시나리오와 대응

| 시나리오 | 결과와 대응 |
|---|---|
| A. 관련 권한을 명시적으로 허용 | 허용된 행위·기간·주기·필드를 분해해 기록. 제3자 권리를 별도로 확인한 뒤 운영 Gate 심사. 허가 확인만으로 즉시 배포하지 않음 |
| B. 부분적으로 허용 | 허용된 작업만 범위를 좁혀 계획. 예: 단기 캐시만 허용되면 장기 보관 제외, 자체 분석만 허용되면 앱 게시 제외 |
| C. 모호한 답변 또는 담당 권한 불분명 | 미확정으로 유지, 정확한 이용 행위별 재문의. 운영 HOLD |
| D. 답변 없음 | 운영 HOLD 유지. P0~P3 기술 PoC 및 자체 콘텐츠 기반 MVP 우선 |
| E. 명시적 불허 | 해당 범위 구현/운영 제외. 기술 검증 코드를 실운영 데이터 수집에 연결하지 않음 |
| F. 허가 후 조건 변경·철회·침해 신고 | 자동 수집·게시 중지, 기존 데이터 공개 차단 및 보존·삭제 조건 재평가, 감사 기록 |

## 5. 기술 PoC / 운영 경계

| 구분 | RSS P0~P3 FROZEN 기술 PoC | 이후 P4 또는 실제 운영(미동결) |
|---|---|---|
| 입력 | 직접 작성한 합성 XML Fixture | 실제 RSS 네트워크 응답(권한 확인 후) |
| 요청 | 실 Google RSS 자동 요청 없음 | 스케줄러 및 폴링(현재 금지) |
| 판정 | C안 후보 선별 + 보수적 A안 제외의 순수 기술 검증 | 실제 데이터 정책 및 실패 처리 추가 검증 필요 |
| DB | 외부 실데이터 영속 저장 없음 | 보존 조건·삭제·출처·감사 경계 확정 필요 |
| 게시 | 외부 실데이터 앱 게시 없음 | 공개 앱 게시 및 콘텐츠 권리 심사 필요 |
| 상태 | FROZEN 계약 유지 | 본 정책 심사를 선행한 후 별도 설계 승인 |

`WOULD_ACCEPT` 등의 기술 판정은 **기술상 후보 적합성**일 뿐 법적 게시 허가 상태를 뜻하지 않는다. 본 v0.1은 P0~P3 계약을 수정하지 않으며, 향후 운영 설계 분리가 필요할 수 있음을 기록한다.

| GATE-0. 대상·이용 목적 정의 | `geo=KR` RSS URL, 수집 주기, 대상 필드, 이용자 범위, 저장 기간 및 공개 목적 문서화 | HOLD |
| GATE-1. Google 자동 접근 권한 | 적용 약관/기계 판독 지시 및 자동 접근 조건 또는 신뢰할 수 있는 서면 확인 | 폴링 차단 |
| GATE-2. Google 데이터 보관·가공 권한 | 데이터 종류별 보존 기간, 가공 및 누적 저장 허용 범위 확인 | 실제 데이터 쓰기 차단 |
| GATE-3. 공개 게시·재배포 권한 | 표시 가능한 필드, 출처 인용 및 공개 대상에 관한 명확한 근거 | 앱 게시 차단 |
| GATE-4. 언론사 권리 | 기사 제목·본문·이미지별 권리/법적 허용 평가와 불허 필드 제외 | 제3자 콘텐츠 제외 |
| GATE-5. 운영 통제 | 요청 빈도·재시도·중단 스위치·삭제/철회 대응·로그·접근 오류 처리·출처 표시 QA | 실제 운영 미승인 |
| GATE-6. 승인 및 추적성 | 책임자 최종 결정, 근거 원본·확인일·허용 범위·재검토 시점 기록 | 배포 보류 |
| GATE-7. 상업 전환(별도) | 비상업적 허가가 상업적 이용까지 포함하는지 별도 확인 | 상업 이용 불가 판정 유지(내부 정책) |

기본 불변조건: **법적 허용 여부와 기술적 적합성을 별개의 상태로 취급한다. 해당 데이터에 필요한 모든 Gate가 통과하지 않으면 `collect → persist → publish` 운영 체인을 활성화하지 않는다.**

## 7. 주요 위험과 추가 확인 항목

1. **약관 적용 범위**: 일반 Google 약관, Google APIs 약관 중 실제 RSS 엔드포인트에 적용되는 문서·추가 조건은 무엇인가?
2. **자동 접근**: Google이 게시한 기계 판독 지시, 요청 한도, `User-Agent`, 캐시·조건부 요청 요건 확인이 남음. 현재는 미검증.
3. **보관 및 삭제**: 원본 XML, 추출 데이터, 표준화된 제목, 시계열 스냅샷, 로그를 동일한 보관 정책으로 다룰 수 없음.
4. **기사 메타데이터와 기사 본문 권리 분리**: URL·제목·매체명·날짜·본문·사진의 권리 위험이 다르며, 단순 사실 예외 적용은 개별 판단이 필요함.
5. **Google 브랜드와 표시**: 데이터 출처는 명확히 밝히되 Google의 제휴·후원·승인 사실을 암시하지 않을 것. 로고 사용은 별도 상표 지침 확인.
6. **자동 게시의 내용 위험**: 중복 이슈, 동명이인·사건사고, 사실관계 변경, 명예·개인정보 등 검증 및 회수 체계가 필요.
7. **외부 AI 이용**: 원문 기사 전송·번역·요약은 데이터 수집/게시의 권한과 별도로 판단.
8. **출처 추적**: 원천 데이터와 자체 정규화·AI 출력 사이의 출처·권한·삭제 연결이 필요.
9. **조건 변경**: 약관·서비스·RSS 필드 변경 및 Google·언론사의 이의제기에 대응할 수 있어야 함.
10. **NAVER 분리**: NAVER API HUB 검색어 트렌드 등의 이용 정책을 Google Trends 해석 근거로 사용하지 않음.

## 8. 11월 중순 MVP A안 영향

- 우선 목표: **적법하게 자체 작성·확보한 실제 Trend를 기존 전체/관심사 목록에 연결**하고 데이터 출처를 추적 가능하게 유지한다.
- Google RSS 자동 폴링·영속 저장·앱 자동 게시는 **MVP 필수 의존성으로 두지 않는다**. 공식 권한 확인 전 운영 경로에는 연결하지 않는다.
- 합성 Fixture의 P0~P3 기술 검증은 별도 진척으로 기록할 수 있지만 **실제 외부 데이터 자동 수집 완료/서비스 운영 완료**로 보고하지 않는다.
- `trends` / `trend_sources` / `trend_rank_snapshots` 등 기존 DB 설계가 있다는 것은 외부 데이터 재사용 허가를 의미하지 않는다.
- 데이터 사용 권한이 확인되면 MVP 종료 이후 별도 운영 설계를 시작하거나, 일정·게이트·테스트 완료 조건이 충족될 때만 포함 여부를 다시 판단한다.
