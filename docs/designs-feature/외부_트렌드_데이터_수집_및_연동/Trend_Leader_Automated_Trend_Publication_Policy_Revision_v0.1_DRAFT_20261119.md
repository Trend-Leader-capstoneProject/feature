## 1. 문제 정의 및 확정된 방향

기존 MVP-A의 개별 담당자 승인 의존성은 지속적인 트렌드 공급이라는 제품 목표를 제한한다. 수집 후보 확보 실패, 인용 불일치 및 Writer 미완성도 별개의 병목이다. 운영 통제의 축소만으로 수집 품질이 향상되거나 게시 경로가 완성되는 것은 아니다.

**사용자 결정(2026-11-19):** 인기 검색어/화제 주제 발견 → 관련 자료 수집 → OpenAI와 Backend 검증 → 제한적 자동 게시를 목표로 한다. 일반·저위험 적격 항목의 건별 사람 승인을 없애고 미확인·위험 항목은 보류/제외한다. 스케줄러가 정상 경로를 사람 개입 없이 수행해야 한다. 이용권한 확인 및 안전한 게시 통제는 유지한다.

| 대안 | 장점 | 한계 | 판단 |
|---|---|---|---|
| 기존 건별 사람 승인 | 세밀한 검토와 직접 책임 | 반복 공급이 승인자의 가용성에 종속 | 기존 수동 프로필에 보존 |
| 무제한 자동 게시 | 구현 흐름이 단순 | 사실·권리·위험 검증 실패가 즉시 공개로 전파 | 제외 |
| 제한적 정책 기반 자동 게시 | 반복 공급과 실패 차단 양립 | 소스별 이용조건, 정책 검증, Writer 안전성 필요 | 사용자 채택 방향 |

**MVP 핵심:** 공급원 한 곳, 관련 자료 탐색원 한 곳, 저위험 주제 범위, 기존 DB와 TrendCard. 다수 소스 통합, 전용 관리자 UI, 분산 워커, 새로운 랭킹 점수, 상세 AI 분석은 후속 범위로 둔다. 실제 소스/비용/주기/근거 수치/저위험 범위는 아직 확정되지 않았다.

## 3. 목표 데이터 흐름 및 책임

```text
Scheduler (실행 제어, 수집 주기, 런 ID, 예산)
  → Discovery Adapter (인기 검색어 또는 관측된 화제 신호)
  → Evidence Discovery Adapter (관련 자료 검색, 후보 URL 확보)
  → Evidence Verification (허용된 자료 확인 + OpenAI 의미 검증 + Backend 검사)
  → Trend Curation (자체 작성 제목/설명, 활성 Child, 근거 연결)
  → Automatic Publication Policy (자동 적격 / 보류 / 제외)
  → Independent Writer (최종 정책·DB 검증, 원자적 등록, Journal)
  → MariaDB → 기존 FastAPI 조회 API → React Native TrendCard
```

| 책임 | 입력 → 출력 (논리 계약, 실제 타입명 미확정) | 경계 |
|---|---|---|
| Discovery | 지역/기간/분야 → 출처별 발견 신호, 관측 시각, 지표의 의미 | 인기 문서·영상·검색어·AI 제안 주제 구분. 없는 인기도 생성 금지 |
| Evidence Discovery | 발견된 주제 → 자료 ID, URL, 제공자, 제목/일자 등 허용 필드 | 검색 결과 수신은 원문 확인·이용권한 증거 아님 |
| Evidence Verification | 허용된 근거 → 관련성·사건 일치·주장별 출처 참조·불확실성 | 모델 판단은 보조. HTTP/DNS/redirect 등 안전 확인, 원출처 사실 대조 및 권리 규칙은 별도 |
| Trend Curation | 근거 있는 주제 → 카드의 정확한 내용 + 활성 Child 후보 | 기사 원문/원제목/이미지 복제 기본 제외, 필요한 요약은 지원 근거 있을 때만 |
| Publication Policy | 후보 내용과 근거, 정책 → 판정·사유·정책 버전·내용 식별값 | 외부 입력/모델이 자동 게시 권한을 발행하지 못함 |
| Writer | 내부 신뢰 경로의 판정 증거와 고정된 내용 → 커밋/차단/롤백/불명확 | 검증 이후 수정·철회·권한 차단, 일반 조회 API와 분리 |
| Delivery | 기존 ACTIVE Trend → 앱 카드 | `GET /api/trends`, `/api/trends/personalized` 유지 |

첫 실증에서는 정량 신호가 비교적 명확한 Wikimedia Analytics 등을 후보로 검토하고, Brave/GNews 등 검색 API를 매칭한다. Wikimedia 페이지 조회수는 급상승 검색량이 아니다. GNews 무료 플랜의 개발·테스트 제약 등은 실제 이용 조건 확인 전 운영 승인으로 취급하지 않는다. 기존 Responses 검색 브랜치는 후보 발견/관련 자료 탐색에 재사용할 수 있으나 객관적인 인기도 공급원은 아니다. 신규 API 채택은 이 문서에서 확정하지 않는다.

### 3.1 첫 카드의 범위 제안

기존 TrendCard를 유지한다. 자체 구성한 트렌드 제목, 활성 세부분류, 검증된 원출처 URL을 최소로 하고, 근거가 뒷받침될 때만 자체 설명을 추가한다. `summary`, `thumbnail_url`, `source_title`의 기존 nullable 계약을 활용하되 실제 UI의 null 동작은 재검증한다. 원제목·원문·이미지 복제와 임의 순위/인기도 표시는 기본 제외한다. 허용된 출처 안내 문구는 현행 A1의 자체 작성 안내 조건 등 관련 계약을 확인 후 사용한다.

## 4. 자동 게시 정책 최소 조건 (제안)

정책은 사람의 승인 의도와 소스 이용 범위를 시스템이 반복 적용할 수 있도록 구성한다. 소스 접근 허용과 외부 AI 전달, 영속화 및 앱 공개를 각각 구분한다. 한 단계에 대한 허가가 나머지 단계까지 허가하지 않는다.

| 확인 조건 | 적격 판단 | 미충족 시 |
|---|---|---|
| 소스 권리 | 발견원, 검색원, 원문 제공자에 대해 해당 행위·필드·목적이 허용됨 | 권리 불명 HOLD, 금지 BLOCKED |
| 실제 원출처 | 안전한 접근 경로, 유효한 원문, 날짜/주장에 맞는 근거 | 접근 불가 또는 근거 부족 HOLD |
| 의미·사건 일치 | 주제와 자료가 관련되고 같은 사건, 핵심 주장별 지원 근거 존재 | 모호/모순 HOLD |
| 위험 범위 | 승인된 저위험 주제 유형이며 사생활·의혹·민감 사고 등 제외 조건 없음 | 고위험 제외, 불명확 HOLD |
| 카테고리 | 기존 활성 Child 매핑 존재 | 임의 기타 분류 없이 HOLD |
| 표시 필드 | 허용된 자체 구성 제목/설명과 원문 링크만 사용 | 필드 정책 위반 BLOCKED |
| 실행 정책 | 현행 정책/소스 범위/운영 프로필 유효, 중단·철회 없음 | 게시 연결·DML 차단 |

최소 근거 기준 제안: 하나의 권리 확인된 1차 공식 자료가 해당 사실을 직접 뒷받침하는 낮은 위험의 사례부터 시작한다. 독립 교차 출처가 필요한 주장, 독립 근거 부족, 불분명한 화제성은 보류한다. 동일 보도자료의 재배포는 별도 독립 근거로 세지 않는다. 근거 수량·최신성·허용 주제 및 금지 주제의 정확한 경계는 소스 선정 이후 최소 계약으로 확정한다. 사용자가 승인한 것은 제한적 자동 게시 방향이며 위 숫자/정책 세부값은 제안이다.

논리 판정명(제안): `AUTO_ELIGIBLE`, `DEFERRED`, `SKIPPED`, `BLOCKED`. 실행 오류는 정상 후보 판정과 구분한다. `AUTO_ELIGIBLE`은 콘텐츠 정책 적격이지 운영 승인·DB 커밋이 아니다. 기존 `WOULD_ACCEPT`, `REVIEW_ONLY`, `ACCEPTED`, `MATCH`를 자동 게시 적격으로 승격하지 않는다.

AI 검증은 정해진 입력 자료 ID에 대한 관련성, 동일 사건 여부, 근거 연결, 모순/불확실성과 활성 Child 추천에 한정한다. 출력 구조와 실제 ID 참조를 Backend가 검사하고, 모델의 자신감이나 인용 모양을 진실/권한의 증거로 사용하지 않는다. 기사 제목·스니펫만 제공한 경우 본문 사실 검증으로 표현하지 않는다. 외부 텍스트는 비신뢰 입력이며 도구 실행/게시 권한을 부여하지 않는다. 원문 자동 접근에는 SSRF, 사설망/IP, 리디렉션 및 DNS 재검증, 타임아웃/크기 제한 등 실제 네트워크 경계를 검증한다.

## 5. G5/G6 및 Writer의 최소 안전 경계

### 바뀌는 것

- 정상 항목의 개별 담당자 승인, 수동 A1 ZIP 제작, 수동 4A/4B 절차, 매회 운영자 실행 입력을 신규 자동 경로의 필수 선행 절차에서 제외하는 **계약 변경 제안**이다. 기존 수동 경로의 증거는 보존한다.
- 운영 프로필을 한 번 승인한 후 Scheduler에 해당 범위 내 실행 권한을 부여한다. 각 실행은 최신 정책과 중단 상태를 검사한다. 운영 변경 시 재검토한다. 정책/프로필의 실제 승인자와 검증 증거는 별도 기록한다.
- 기계적 적격 기록은 게시 값의 정확한 스냅샷/식별값, 출처와 근거 참조, 결과·사유, 정책 버전, 실행 ID, 판정 시각을 담는다. 보호된 정책/판정 기록 및 발행 주체를 Writer가 독립적으로 검증한다. 해시나 `approved=true` 선언만으로 권한을 증명하지 않는다.

### 바뀌지 않는 것

- 별도 실행 책임을 가진 Writer, 보호된 영속 Journal, 실제 DB/계정/GRANT 확인, 일반 API의 Trend 쓰기 차단, 승인 범위 밖 DB 연결/쓰기 차단.
- 확정 Batch의 전체 Commit/Rollback. 이 초기 제안에서는 **Batch 크기 1**로 운영하여 복잡한 부분 성공 정책을 피하고, 이후 다건 확장 시 기존 P4-DEC-04와 정합성을 재검토한다. 후보 선별 중 부적격 제외와 확정 Batch 실패를 구분한다.
- 제목/Source 중복 및 DB UNIQUE/FK 최종 방어, 활성 Category 재검증, `HIDDEN` 자동 복구 금지. 동일 제목 다른 사건이 모호하면 보류. 초기에는 기존 Trend 자동 갱신보다 안전한 신규 등록 및 중복 건너뛰기를 제안한다. `last_collected_at` 자동 갱신 정책은 SD-009와 별도 대조한다.
- 승인/정책 변경과 Writer의 공유 조정 경계, 커밋 전 철회 시 차단/롤백, 커밋 후 공개중단(`HIDDEN`과 조회/API 캐시 확인), 기록 손상/커밋 결과 불명 시 신규 게시 전역 HOLD 및 수동 대조. 다음 스케줄이 알 수 없는 커밋 결과를 자동 재시도하지 않는다.
- 기존 `Trend.status`가 ORM/서버에서 기본 ACTIVE인 만큼 미승인 후보의 임시 INSERT 금지. 미승인 실데이터는 운영 DB에 HIDDEN으로도 사전 적재하지 않는다.

수집 실패는 해당 수집 실행에 기록하고 다음 예정 수집은 허용된 범위에서 진행할 수 있다. 게시 트랜잭션 결과 불명/권리 철회/Journal 무결성 문제는 별도 전역 게시 차단으로 처리한다. 수집 신규 실행과 동일 쓰기 재시도를 혼동하지 않는다.

## 6. 개발 로드맵 — 문서가 병목이 되지 않도록

기존 RSS P0~P4와 혼동하지 않도록 새 작업 ID는 AP-0~AP-4로 구분한다. AP는 가칭이다. 한 단계마다 실행 가능한 결과와 종료 조건을 남긴다. 새 관리자 UI/Schema/복잡한 인프라를 먼저 만들지 않는다.

| ID | 개발 작업 | 종료 기준 | 선행 경계 |
|---|---|---|---|
| AP-0 | 본 정책 개정 검토 + 공급원/검색원 1개씩 선정 | 적용 필드와 접근/저장/AI/공개 범위 확인, 다음 구현 범위 고정 | 권리 미확정 실요청 금지 |
| AP-1 | Discovery → Evidence Discovery 단건 읽기 전용 PoC | 실제 발견 신호와 관련 URL 1건 이상 연결, 정상/빈 결과/오류/무관 후보 기록 | 기존 게시 HOLD 유지 |
| AP-2 | OpenAI + Backend 검증 및 카드 Preview | 정확한 근거 연결, 위험/모호/무관/중복/가짜 참조 차단 | 외부 AI 전달 허용 자료만, 게시 0건 |
| AP-3 | 자동 적격 정책 + 최소 독립 Writer/Journal 격리 검증 | 개별 사람 승인 없이 합성 적격 건의 원자적 commit, 미적격 쓰기 0, 중단/철회/중복/불명확 차단 | 세부 계약 승인, 격리 DB 한정 |
| AP-4 | 운영 프로필 승인 후 실제 공급 및 Scheduler E2E | 허용된 실데이터 1건 이상 앱 제공, 반복 자동 실행 및 실패 방어 | G0/G4~G6 개정 조건 및 관련 권한 증거 충족 이후만 |

AP-1·2와 AP-3의 안전성 검증 준비는 병행 가능. 새 소스를 결정할 때마다 운영 정책 전체를 다시 작성하거나 기존 수동 승인 도구를 새로 완성하는 것은 선행 조건으로 삼지 않는다. 필요한 소스 범위와 변경되는 불변조건만 해결한다. 운영 조건이 충족되기 전에는 실제 외부 공급 경로를 읽기 전용으로 제한한다. 공급원 한 곳에서 실패할 경우 기록하고 다음 후보를 검토하며 무한 재시도, 출처 제한 우회를 하지 않는다.

## 7. 최소 Acceptance Criteria (제안)

| ID | 합격 기준 |
|---|---|
| AC-01 | 허용된 실제 Discovery 신호 1건 이상에서 관련 자료 URL과 관측/출처 의미를 기록한다. |
| AC-02 | 같은 사건의 지원된 핵심 주장과 실제 입력 근거 참조로 카드 Preview를 생성한다. 무관/모순/허용 범위 외 출처/모델 오류는 적격 0. |
| AC-03 | 격리 테스트에서 승인된 정책의 저위험 합성 후보는 사람의 건별 입력 없이 등록된다. 미적격 후보나 운영 프로필 HOLD는 서비스 DB 연결 및 쓰기 0. |
| AC-04 | 반복 발견, 두 실행의 경합, UNIQUE 충돌, 중간 실패 및 결과 불명 시 중복 Trend 0, 필요한 경우 전체 rollback/게시 HOLD. 철회·HIDDEN 자동 복구 방지. |
| AC-05 | 합성 시험으로 정책 변경/스냅샷 불일치, 실제 DB 대상·권한 불일치, Journal 손상 및 공개중단 동작을 검증한다. |
| AC-06 | 운영 승인 후 실제 후보 1건이 사람의 건별 승인 없이 DB→API→실기기 TrendCard까지 연결되며 원출처 링크가 정상이다. |
| AC-07 | 제안 목표: 독립 실행 3회 이상, 그중 Scheduler에 의해 사람 개입 없이 개시·처리된 실행을 별도 입증한다. 신규/중복/보류/오류/등록 건수를 구분한다. 최종 다양성 목표는 최소 3개 대분류 실데이터로 유지 검토한다. |

AC-01/02만 충족하면 읽기 전용 공급 PoC 성공이지 자동 게시 성공이 아니다. AC-06/07 및 적용 운영 조건까지 입증해야 자동 공급 MVP 완료를 선언한다. 위 숫자는 이전 계획을 계승한 제안이며 팀/평가자의 공식 합격 수치가 아니다. 자동 게시가 가능하더라도 화제성 발견 신호와 콘텐츠 사실 확인은 별개 결과로 기록한다.

## 8. 구현 전 남은 결정과 바로 다음 작업

이번에는 결정 목록을 작게 유지한다.

1. AP-1 입력원과 검색원 선택: 어떤 실제 데이터 필드가 필요한가, 접근·검색 결과 처리·AI 전달·저장·앱 공개 범위는 어디까지 허용되는가. 권한 불명 시 해당 동작은 HOLD.
2. AP-1 실행 예산/요청 상한/후보 상한: 실제 계정·환경 확인 후 고정. 최초 단건 실증은 합성 검증부터, 유료/라이브 실행은 별도 범위 승인 후 진행. 기존 Responses CLI의 TTY 확인을 몰래 제거하지 않는다.
3. AP-2/3 시작 시 저위험 허용 규칙·근거 충분성·자동 판정 증거 연결·Journal/철회 조건을 해당 작업에 필요한 최소 범위만 확정. 새 운영 프로필의 승인 주체와 배포 환경은 실제 운영 전에 확정.

**다음 작업은 AP-1을 위한 공급원 두 개 선정 및 단건 연결 PoC이다.** AP-0의 정책 방향을 반복해서 재토론하지 않는다. 구현 시작 시 최신 HEAD/Worktree/실제 코드·테스트와 대상 브랜치 확인 후, 기존 RSS Parser와 Responses 계약을 변경하지 않는 최소 Adapter 연결을 설계한다. 필요하면 기존 Normalizer의 순수 함수만 공유하며 Google 전용 파싱 계약에 다른 공급원 구조를 억지로 넣지 않는다.
